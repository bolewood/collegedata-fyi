# Design: Discovery Freshness — Date Observability + Per-School Publish Alerts

Generated by /office-hours on 2026-08-18
Branch: santhonys/mirror-pr-notify-review
Repo: bolewood/collegedata-fyi
Status: SUPERSEDED — see docs/prd/029-discovery-freshness-and-publish-alerts.md
Mode: Builder

**Superseded 2026-08-18** by `/plan-eng-review` + an outside-voice (Codex)
pass, which found the feed-on-`cds_documents` architecture below was
unsound (mutable rows can't safely drive an RSS feed; `refreshed` updates a
row rather than inserting one, contradicting this doc's own success
criterion; a new row doesn't always mean "the school published" because
`source_provenance` includes mirror and operator-manual origins). The
numbered PRD carries the corrected design — an append-only publish-events
table, `source_provenance`-filtered alerts, and `source_http_last_modified`/
extracted-metadata dates in place of `discovered_at` as the freshness
signal. This file is kept for the historical record of how the idea was
shaped, not as the implementation reference.

## Problem Statement

Two related gaps. First, school/year pages don't show collegedata.fyi's own
pipeline timestamps (when a CDS file was discovered, when it was extracted)
alongside the document's own vintage, so a visitor can't tell how fresh the
archive's read of a school is. Second, there's no way for someone who cares
about one school (a parent refresh-mashing UPenn's IR page every day in the
fall admissions cycle) to get notified the moment a new CDS is found, without
collegedata.fyi collecting emails/phones or building push infrastructure.

## What Makes This Cool

A per-school RSS/Atom feed makes "subscribe to my school's CDS" a
zero-infrastructure, zero-PII feature — no email list, no push service, just
a URL any RSS reader or notification bridge already knows how to consume.
Paired with visible discovery/extraction dates, the site starts explaining
its own freshness, not just the document's freshness.

## Constraints

- No new automated-crawling infrastructure needed for the baseline case —
  `archive-enqueue`/`archive-process` already re-check every school in the
  corpus weekly, year-round, via Supabase pg_cron (confirmed live since
  2026-04-15).
- `cds_documents.discovered_at` exists today; there is no `extracted_at`
  column — only an `extraction_status` CHECK-constrained text column (not a
  native enum) with no timestamp on the `extracted` transition.
- The cooldown scheduler (`archive-enqueue/schedule.ts`) is currently a flat
  function of `(last_outcome, now)` — no per-school tiering, no concept of
  elapsed time since a school's actual last CDS.
- Historical `discovered_at` values have no documented backfill/trustworthiness
  guarantee before this feature ships — mitigated by the bootstrap rule below
  rather than picking an unverified cutover date.

## Premises

- The site's existing weekly-for-everyone discovery cadence is not a gap to
  fill — it already does more than initially assumed. (Corrected mid-session
  after an initial wrong claim that no automation existed at all.)
- PRD 019 (change intelligence) is adjacent but distinct: it emits
  field-level *delta* events (admit rate moved) behind a human-review gate
  before going public. This feature emits raw *existence* events (a new
  document was found) with no inference risk, so it doesn't need PRD 019's
  review queue.
- "9 months after last publish" is a demand-side heuristic (annual documents,
  near-zero chance of a new one shortly after the last), not a hard rule —
  worth validating once real subscriber data exists.

## Approaches Considered

### Approach A: Minimal — UI + plain feed, no escalation
Ship date-observability UI and a per-school RSS feed off the existing weekly
cadence; defer tiered daily escalation. Ruled out as the sole approach: caps
the fall-refresh use case at up to 7-day lag indefinitely, and the escalation
piece turned out cheap enough not to defer.

### Approach B: Full — escalation shipped alongside the UI (CHOSEN)
Same UI and feed, plus a top-50 tier that escalates from the default 7-day
cooldown to daily once a school is 9+ months past its last *trustworthy*
`discovered_at`. Note this clock runs off when we found the document, not
when the school actually published it — under the baseline cadence that lag
is typically up to 7 days (longer after a failure outcome; see
`DEFAULT_COOLDOWN_DAYS`), so "9 months since discovered_at" slightly
undercounts true time-since-publish. Not worth correcting for v1, but worth
naming so the threshold isn't read as more precise than it is.
"Trustworthy" is bootstrapped per school: a school stays on the default
cadence until it produces its first fresh discovery event after this feature
ships; only then does its 9-month clock start. On ship day this is
behaviorally identical to Approach A for nearly every school — it only
diverges months later as schools individually lock on.

### Approach C: A/B plus a visible "actively monitored since {date}" badge
Not ruled out — folded into Approach B's scope as a candidate UI element,
since the lock-on bootstrap state is otherwise invisible plumbing and the
badge would make it an honest trust signal instead.

## Recommended Approach

B, with C's badge as an in-scope UI candidate. The escalation logic is inert
until a school locks on, so there's no risk of a false or premature alert to
users from shipping it now instead of deferring to a second PRD. That is
narrower than "no risk" overall: it's still a change to the production cron
scheduler that runs against the full corpus daily, which is exactly why Next
Steps #6 calls for a dedicated `/plan-eng-review` pass on the scheduler
change before merge — not a contradiction of "ship it now," but the specific
gate that change needs regardless of which approach carries it.

## Open Questions

- `extracted_at` semantics: add a real timestamp column set only at the
  `extraction_status → extracted` transition. Deriving it from `updated_at`
  is not a viable fallback — `cds_documents_updated_at` (the row trigger in
  `20260413201910_initial_schema.sql`) bumps on *any* column update, not
  just extraction, so it would silently misreport extraction time after an
  unrelated later edit (e.g. a `data_quality_flag` change).
- Top-50 list: reuse `data/watchlists/top_200_change_intelligence.yaml`
  trimmed to 50, or hand-curate a different set — not decided.
- Feed format and URL shape (RSS 2.0 vs Atom; `/schools/{id}/feed.xml` vs a
  query param) — not decided.
- Feed granularity: `cds_documents` allows multiple rows per school+year via
  `sub_institutional`, so a single publish event could produce more than one
  document row. Decide whether each sub-institutional filing gets its own
  feed entry or they collapse to one per school+year.
- Which `ProbeOutcome`s are feed-worthy: `inserted` (new year) and
  `refreshed` (same year, corrected content) both represent real new bytes
  and should fire; `unchanged_verified`/`unchanged_repaired` should not.
- Retraction handling: two independent, unrelated paths can remove a
  document after subscribers already received a feed entry for it — ADR
  0008's human takedown process (sets `participation_status = 'withdrawn'`)
  and the automated pipeline's own dead-link detection (`marked_removed`, a
  `ProbeOutcome` written when a re-check finds the upstream URL gone). RSS/
  Atom has no built-in retraction for either. At minimum, document this as a
  known limitation for v1; decide later whether a correction entry gets
  emitted for one or both paths.
- De-escalation: tier escalation should only widen the *success*-outcome
  cooldown window (7d → 1d), never override the existing failure-outcome
  backoffs (`auth_walled_*` 90d, `dead_url` 14d, etc. in
  `DEFAULT_COOLDOWN_DAYS`). Otherwise a locked-on top-50 school that starts
  404ing could get probed daily forever with no de-escalation path, unlike
  every other outcome category in this scheduler.
- School-page placement: this feature's UI (dates, "actively monitored
  since" badge) needs to be reconciled with PRD 019's already-planned "What
  Changed" module and `/changes` page, which target similar school-page real
  estate — sequencing/placement isn't decided.
- Feed retention/pagination (all history vs. recent-only) and rate-limiting
  for the new public per-school endpoint — not decided; a reasonable v1
  default is "last N entries, unauthenticated, standard CDN caching."
- Whether Approach C's badge ships in the same PR as the feed or as a
  fast-follow.
- Whether the 9-month/daily thresholds need to be configurable per-school
  (e.g., known December-publishing schools) or are fine as global constants
  for v1.

## Success Criteria

- School and year pages show discovery/extraction dates in view-source (not
  just visually), matching PRD 028's "coverage-honest copy" bar.
- A subscriber to a top-50 school's feed sees a new-document entry within 1
  day of the school publishing, once that school has locked on *and* its
  9-month clock has elapsed (i.e. escalated to daily — lock-on alone does
  not imply daily checking yet).
- No false "new document" entries — the feed only fires on genuine new
  `cds_documents` rows, never on a re-verification of an unchanged file.

## Distribution Plan

Existing deployment pipeline covers this — new UI and API surface on the
already-deployed Next.js/Supabase stack, not a new distributable artifact.

## Next Steps

1. Decide the `extracted_at` schema question (Open Questions #1) — blocks
   both the UI and any future extraction-latency reporting.
2. Trim/confirm the top-50 tier list (Open Questions #2).
3. Spec the feed format and URL pattern (Open Questions #3), including how
   it excludes withdrawn/removed documents per ADR 0008's takedown process.
4. `archiveCooldownDaysForOutcome`'s real signature is `(outcome, now)`
   with no school identity and `now` currently unused — escalation needs a
   signature and call-site change (`archive-enqueue/index.ts` passes tier +
   lock-on state in), not an in-place branch on the existing function.
   `public.institution_directory` does have a `school_id`-unique row per
   school and could technically take a new column, but its migration
   documents a single-writer convention (`tools/scorecard/load_directory.py`
   is the only supported writer) that an escalation-state column written by
   `archive-enqueue` would violate. Add a migration for a new side table
   keyed by `school_id` holding the lock-on marker (e.g.
   `escalation_eligible_since`) instead, mirroring the existing
   `school_hosting_observations` pattern.
5. Ship school/year page date UI, feed endpoint, and (if in scope) the
   "actively monitored since" badge.
6. Recommend `/plan-eng-review` next to lock the schema and scheduler-change
   details before code — this touches a cron job that runs against
   production daily, worth a second pass before merge.
